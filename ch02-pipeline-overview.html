Vol. 02 · Pipeline Overview

Camera Pipeline 全景圖
從 sensor 到 display 中間 發生了什麼

你按下快門那一刻,有幾十個模組同時在動:sensor 還在曝光、ISP 在跑前一張、 AE 在算下一張的曝光、encoder 在等 buffer、display 在重新整理 preview。 這一章把整條路展開,讓你看清楚每一塊在做什麼、彼此怎麼握手。

Section 01 · 系統全景

整條 pipeline 到底有多少塊磚

從硬體角度看,一個現代手機 camera 系統至少包含:Camera module(sensor + lens + VCM)、 MIPI CSI-2 介面、CSI receiver(在 SoC 內)、前端 ISP、DRAM、後端 ISP、encoder、display。 每一塊都有自己的 clock、power domain、buffer。

▸ 完整 camera pipeline 資料流

完整 camera pipeline:資料從 sensor 經 MIPI 進入 SoC,前端 ISP 先處理 raw,寫回 DRAM,後端 ISP 再做進階運算,最後分流到 encoder(存檔)與 display(預覽)。3A 統計值由前端 ISP 內的 HW stats engine 從 raw/Bayer domain 採集,DMA 給 camera firmware/DSP 跑 AE/AF/AWB 演算法,再經 I²C 寫回 sensor 與 VCM(深入見 Ch05)。

Section 02 · 前端 vs 後端 ISP

為什麼 ISP 要切兩段 那條虛線在哪

你會在規格表看到「Front-end ISP / Back-end ISP」這個分法。簡單講就是:前端做 raw domain 的事(每張都要做、沒得省)、後端做 YUV/RGB domain 的事(可以挑選性做、跨幀做)。 切分原因是頻寬與功耗。

區段 資料格式 典型處理 是否每幀都做
Front-end ISP Bayer raw BLC、LSC、defect 校正、demosaic、WB、HDR merge 每張必做
Back-end ISP YUV / RGB tone mapping、NR、sharpen、CCM、gamma、scale 可選擇路徑
Multi-frame engine YUV(或 raw) HDR/夜景合成、align、merge、ghost removal 只在拍照時跑
為什麼這個切分省功耗
  • 前端的輸出寫入 DRAM 時通常已經 demosaic + WB + 縮小,後端要的資料量降低
  • Preview 路徑可以走「短路」——前端直接縮圖出 1080p 給 display,跳過後端複雜運算
  • Capture 路徑才把 full-res 餵給後端,集中力氣處理「使用者最終會看的那張」
補充 · 名詞速查

表格裡的縮寫 先解一遍

上面表格裡冒出來的 BLC、LSC、demosaic、CCM、MFNR…這些是 raw/YUV domain 的標準術語。 這裡先給一句話的「decoder」,深入原理留到後面各章。順序也是 pipeline 真實的執行順序 ——記住順序,等於記住背後的物理邏輯:先處理「跟內容無關的固定誤差」,再處理「跟內容有關的色彩/雜訊」。

縮寫 全名 一句話解釋 深入
BLC Black Level Correction sensor 沒光時讀出來也不是 0(有 dark current offset),要先減掉 Ch04
DPC Defect Pixel Correction 修掉死點/熱噪點,分 static(OTP 標好)和 dynamic(運行時偵測) Ch04
LSC Lens Shading Correction 透鏡邊角進光少(cos⁴θ),乘一個 gain map 把暗角拉回來 Ch04
Demosaic — Bayer 1 通道插值成 RGB 3 通道,前端 ISP 最吃算力的一步 Ch04
WB / AWB (Auto) White Balance 對 R/G/B 各乘 gain,讓不同色溫光源下「白色」呈現白色 Ch05
CCM Color Correction Matrix 3×3 矩陣把 sensor 的 RGB 色域映射到 sRGB 標準色域 Ch06
Gamma — display 響應曲線補償 + 把線性訊號做非線性壓縮 Ch06
Tone Mapping — 把 14 stops 真實世界 DR 壓到 8 stops display;LTM(local)算力大戶 Ch06
NR Noise Reduction spatial(單張內)+ temporal(跨幀);後者效果好但要 frame buffer Ch06
MFNR Multi-Frame Noise Reduction 對齊 N 張 raw 平均,SNR 提升 √N,夜景模式核心 Ch07
HDR merge — 短/中/長曝合成出高 DR;動態物體易 ghost,要 motion detection Ch07
Binning — sensor 端 2×2 / 4×4 pixel 合併,降解析度換 SNR + 省 readout 頻寬 Ch01
VCM Voice Coil Motor 對焦馬達,AF 控制的就是它(移動 lens 改變焦距) Ch01
MIPI CSI-2 — sensor↔SoC 高速差分介面,2~4 lanes × 1.5~4.5 Gbps/lane;頻寬瓶頸 Ch03
DMA-buf — Linux zero-copy buffer 共享,sensor→ISP→encoder 不用 memcpy —
ZSL Zero Shutter Lag 取景時就一直存 raw 到 ring buffer,按快門當下取最近的那批 本章 §3
3A AE + AF + AWB Auto Exposure / Focus / White Balance 三條獨立的回授迴路 Ch05
順序背後的物理邏輯(記這個就夠了)
  • BLC 永遠在第一步——後面所有運算都是線性乘法,如果 0 不是真的 0,誤差會被放大
  • LSC 要在 demosaic 之前——shading 是 per-channel 偏差,要在 Bayer domain 校正
  • Demosaic 要在 CCM 之前——CCM 是 3×3 矩陣乘,需要 R/G/B 三色齊全
  • NR / sharpen 在後端——這些跟「內容」有關,需要先有乾淨色彩才能談
Section 03 · Preview vs Capture vs Video

同一條 pipeline 三種使用情境

使用者只看到「按快門」和「錄影」,但內部其實有三種非常不同的 pipeline 配置: preview path(取景中,要低 latency)、 capture path(按快門那瞬間,要最高畫質)、 video path(連續錄影,要穩定 fps)。

P

Preview Path(取景)

目標:60fps、< 100ms motion-to-photon latency

Sensor 用 binning 模式輸出 4K → 前端 ISP 縮成 1080p → 後端做輕量 tone mapping → 送 display。跳過所有 multi-frame 處理,因為使用者只是在「看」。 這條路徑的 KPI 是 motion-to-photon latency——你手晃動到畫面更新之間的時間。

C

Capture Path(拍照)

目標:最高畫質,latency 預算 200~800ms

按下快門那一刻,系統會啟動「Zero Shutter Lag(ZSL)」機制——其實畫面早就在拍了, sensor 一直把最近幾張存在 circular buffer 裡,使用者按快門時取出時間點最接近的那批, 送進 multi-frame engine 做 HDR / 夜景合成。所以「快門感覺很即時」, 但其實後台正在處理 4~10 張 raw。

V

Video Path(錄影)

目標:穩定 fps、不能 drop frame

Sensor 持續輸出 30/60/120 fps,前端 ISP 即時處理後 直接送 encoder, 不經過 multi-frame。最大壓力來自固定 frame budget:30fps 就只有 33ms 預算, 120fps 就只剩 8ms。任何環節超時都會 drop frame,使用者立刻看到卡頓。

Scenario · 你按一次快門背後發生的事
1 → 取景中,sensor 一直以 30fps 跑,前 8 張 raw 始終存在 ZSL ring buffer
2 → 使用者按下快門,APP 發 capture request 給 camera HAL
3 → HAL 從 ring buffer 取出最近 N 張 raw,標記 capture 時間點
4 → 同時觸發 sensor 再拍 2 張不同曝光(HDR 長/短曝)
5 → Multi-frame engine 對齊 → 合成 → 後端 ISP 加強 → encoder 出 JPEG
6 → 儲存到磁碟,通知 gallery,整個流程約 300~600ms
Section 04 · 軟體堆疊

從 App 到硬體 中間有多少層

系統工程師面試最容易被問到的是「資料路徑上有多少 software stack?」。Android 上一個典型的 camera 呼叫路徑如下。

# Android Camera 軟體堆疊 App(Java/Kotlin) │ Camera2 / CameraX API ▼ Camera Framework(camera service) │ AIDL / Binder IPC ▼ Camera HAL3(Vendor 實作) │ e.g. camx + chi-cdk(Qualcomm) │ e.g. imgsensor + mtkcam(MediaTek) ▼ Kernel driver │ v4l2 / DMA-buf ▼ ISP / CSI hardware │ ▼ Sensor(I²C 控制 + MIPI 資料) ⚠ 每一層都會引入 latency 與 buffer
Stack · 系統工程師面試常被深入問
  • Camera HAL3——Android 的 vendor HAL 介面,規範了 request/result 模型
  • camx / chi-cdk——Qualcomm 的 camera framework,智慧眼鏡開發會直接碰
  • mtkcam(Hal3a)——聯發科的 camera HAL 實作,你應該很熟
  • DMA-buf——zero-copy buffer sharing,sensor → ISP → encoder 之間就靠它
Section 05 · 本章重點回顧

Pipeline 全景 面試最常考的觀念

記住這幾件事
1 → 前端 ISP 處理 raw,後端 ISP 處理 YUV——切分是為了省 DRAM 頻寬與功耗
2 → Preview / Capture / Video 是三條獨立的路徑,但共用前端 ISP
3 → ZSL(Zero Shutter Lag)讓快門「秒回」,核心是 ring buffer
4 → 3A 是一個回授迴路:前端 ISP 的 HW stats engine 從 raw 採集統計值,firmware/DSP 跑演算法,再經 I²C 寫回 sensor 與 VCM
5 → Camera HAL3 + camx/chi-cdk 是 Qualcomm 平台必懂的字典
Section 06 · 講稿練習

面試白板題 30 秒 raw → display 講稿

面試很容易被要求「在白板上畫一下 camera pipeline」。下面這段是一個 30 秒版本的講稿—— 不是要你背下來,而是讓你練到能「邊畫邊講」、把上面表格裡所有縮寫的順序串起來。 畫一個簡單的方塊圖(sensor → 前端 ISP → DRAM → 後端 ISP → encoder/display), 講到對應的方塊時用手指點一下,效果最好。

Script · 30 秒講稿(從 raw 到 display)
1 → 「Sensor 出來的是 Bayer raw——每個 pixel 只有 R/G/B 其中一色。」
2 → 「但 raw 不是『光的真實值』,所以前端 ISP 先做三件清理:BLC 把暗電流 offset 減掉,LSC 把鏡頭邊角暗角拉回來,DPC 把壞點補掉。」
3 → 「有了乾淨 raw,demosaic 把 1 通道 Bayer 插值成 3 通道 RGB,這時候才有完整三色可以做 WB 跟 CCM,把 sensor RGB 校正到 sRGB 色域。」
4 → 「寫進 DRAM 之前通常已經是 YUV 縮圖了——這是省 DRAM 頻寬的關鍵設計,也是前後端 ISP 切兩段的原因。」
5 → 「後端 ISP 再做 tone mapping、NR、sharpen,最後分流到 encoder 跟 display。順帶一提,3A 統計值是前端 ISP 的 stats engine 採集,DMA 給 firmware/DSP 跑演算法後,經 I²C 回授去調 sensor 曝光與 VCM 焦距。」
6 → 「如果是拍照,還會多走一條 multi-frame 路徑——從 ZSL ring buffer 取最近幾張 raw,做 HDR 或 MFNR 合成。」
講稿練習建議
  • 計時練——目標 30 秒講完,超過代表細節太多;少於 20 秒代表骨架沒打到
  • 「為什麼」要能跟答:面試官常會打斷問「為什麼 BLC 是第一步?」、「為什麼前後端要切兩段?」——上一節「順序背後的物理邏輯」就是答案
  • 準備 follow-up:從這段講稿能自然延伸到 Ch12 硬體層 perf/power trade-off(「那這條 pipeline 在硬體上怎麼省電?」)——這是 camera performance 職位的真實切入點
