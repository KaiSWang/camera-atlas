Vol. 12 · HW Architecture & Perf-Power Trade-offs

硬體層看 ISP
SRAM 在哪、DRAM 多痛、真正能優化什麼

前面章節談的是 ISP 演算法在做什麼。這一章換個視角: 把 ISP 攤平到 silicon + memory hierarchy 上,看每一個演算法節點背後的 SRAM 需求、DRAM 頻寬代價、以及 performance engineer 真實能動的旋鈕。 讀完之後,你看到一條 camera pipeline 不會只看到資料流,而是看到 memory traffic 與 power domain 的地形圖。

Section 01 · Memory Hierarchy

ISP 的記憶體階層 三層,差兩個數量級

ISP 上跑的演算法形狀,根本上是被 memory hierarchy 塑造的。三層由近到遠: register file(在 PE 旁邊)、on-chip SRAM(line/tile buffer)、 off-chip DRAM(系統共用 LPDDR)。每往外一層,能量代價跳一個數量級。

▸ Memory hierarchy 的能量與頻寬

能量數量級:DRAM access 大約是 on-chip SRAM 的 50–100 倍。這個比例不是抽象學術數字,它直接決定了 ISP 的演算法形狀——能在 SRAM 上 streaming 完的,絕不繞 DRAM 一圈。

記住這一句,後面所有 trade-off 都從它推導
  • DRAM access ≈ 50–100× SRAM access(就能量而言)
  • 所以「能不能避免一次 DRAM round-trip」就是 ISP HW 設計最大的優化目標
  • 而能不能避免,完全看你SRAM 夠不夠裝下你要處理的 window
Section 02 · 處理粒度

Line / Tile / Frame 三種粒度,三種代價

ISP 處理一張影像,有三種粒度可以選——每種對 SRAM 與 DRAM 的需求不同, 也決定了能跑哪些演算法。理解這三種粒度,你就懂為什麼前端 ISP 能 streaming、 後端 ISP 為什麼一定要碰 DRAM、tile mode 是用來折衷什麼的。

粒度 SRAM 需求 DRAM round-trip 能跑哪些演算法
Line-based
(streaming)		 幾條 line(~ kernel height) 不必 BLC、LSC、DPC、demosaic、spatial NR(小 kernel)
Tile-based 1 個 tile(例如 256×256) 每個 tile 一次 大 kernel NR、LTM(local tone mapping)、複雜後處理
Frame-based 需要整張前一幀 每幀必走 MFNR、HDR merge、temporal NR、EIS warp
為什麼前端 ISP 能 streaming(這是省電關鍵)
  • 前端的演算法 kernel 都很小(3×3 ~ 9×9),只要 SRAM 裝得下幾條 line 就能滑動處理
  • Sensor 把 raw 一行一行送進來,ISP 一行一行處理、一行一行送出去——整條前端不需要回頭看 DRAM
  • 這也是為什麼 Ch02 §2 講「前端 ISP 是每張必做、後端可選擇」——前端做的事 SRAM 就能 handle,代價極低
  • 後端要跨 tile / 跨 frame,SRAM 不夠裝,只能 DRAM round-trip;這也是後端為什麼比較貴
Section 03 · 每個節點的 SRAM 開銷

Pipeline 節點 × SRAM 需求 面試經典題

把 Ch02 名詞速查 裡的每個節點,標上「需要多少 SRAM」、「能不能 streaming」。 這張表能讓你在面試時被問「為什麼 demosaic 比 BLC 貴 100 倍 SRAM?」時,30 秒內答得出來。

節點 典型 SRAM 需求 能 streaming? 為什麼
BLC ~ 0(per-pixel offset) 可 每個 pixel 獨立減常數,不需要鄰居
LSC tiny(17×13 ~ 33×25 grid + 內插暫存) 可 gain map 預存 SRAM,即時 bilinear 內插
DPC 3–5 lines(3×3 ~ 5×5 kernel) 可 看周圍 8 個 pixel 中位數即可
Demosaic 5–9 lines(edge-aware kernel) 可 需要 5×5 或 7×7 鄰域才能判斷邊緣方向
WB / CCM / Gamma ~ 0(per-pixel matrix/LUT) 可 純 per-pixel 乘法或查表
Spatial NR
(bilateral / NLM)		 5–25 lines(kernel 越大效果越好) 可(line-mode) kernel 大小直接吃 SRAM,設計時 trade off 畫質 vs SRAM 面積
LTM
(Local Tone Mapping)		 1 個 tile(~ 256×256) tile-mode 需要看「區域」統計才能做局部曝光,不可能只看一條 line
Temporal NR 整張前幀 → DRAM frame-mode SRAM 裝不下整張,只能放 DRAM。這就是後端 DRAM 流量的主源
MFNR / HDR Merge 多張完整 raw → DRAM frame-mode 對齊 + merge 需要同時看 N 張,SRAM 完全不可能
EIS warp 整張 + 周邊冗餘 → DRAM frame-mode warp 映射可能讓任意 source pixel 跑到任意 dest 位置
這張表的三個 takeaway
  • raw-domain 的東西基本都能 streaming——這就是前端 ISP 「便宜」的根源
  • 「需要看區域」或「需要跨幀」就被迫離開 SRAM——LTM、temporal NR、HDR merge、MFNR、EIS 都是這類
  • 所以「把多少東西做進前端 ISP」是 silicon 架構師的核心 trade-off:做進去佔 SRAM/silicon area,做不進去走 DRAM 燒電
Section 04 · 頻寬數學

把 DRAM 流量算給你看 數字會嚇你一跳

面試常被問「你怎麼估算這個 use case 的 DRAM 頻寬?」——這不是難題,只要會單位轉換。 下面拿一個典型場景算給你看,讓你習慣這個量級。

# Use case: 50MP sensor @ 30fps 10-bit Bayer raw Sensor stream: 50,000,000 px × 10 bit × 30 fps = 15,000,000,000 bit/s = ~ 1.75 GB/s # 只是 sensor → CSI,還沒到 DRAM Front-end ISP 寫 DRAM(輸出 YUV420 縮成 4K): 3840 × 2160 × 1.5 byte × 30 fps = ~ 0.37 GB/s # 已 demosaic + downscale,流量降一個數量級 Back-end ISP 讀 DRAM(全幀): 0.37 GB/s(讀)+ 0.37 GB/s(再寫回) = ~ 0.74 GB/s # round-trip 翻倍 Temporal NR 額外讀前幀: + 0.37 GB/s Encoder 讀: + 0.37 GB/s ⚠ 光是 camera path 就吃掉 ~ 1.85 GB/s DRAM 流量 ⚠ 還沒加上 display refresh、UI、AI 推論、其他 client
為什麼這個數字重要(這是你跨進 camera 的 PMQoS 視角)
  • LPDDR5x peak 大概 50 GB/s,但 camera 通常只能拿 5–15 GB/s 的 share(其他 client:CPU、GPU、display、NPU、modem)
  • 所以「DRAM 頻寬」是 system-level constraint——這正是你在 MTK 做 PMQoS 時處理的同一個東西(EMI bandwidth)
  • Camera + display + encoder 同時跑就會出現 memory contention——某個 client 拿不到頻寬,就會 frame drop 或 underrun
  • 「房東/房客」的比喻搬過來:DRAM 頻寬就是房東,camera/display/encoder/NPU 都是房客;PMQoS 在這層做仲裁
Section 05 · 優化技術

Performance engineer 真實能動的旋鈕 (6 個)

理解 trade-off 之後,真正能做的優化大致就 6 類。 Camera performance 工程師日常 80% 的工作,就是在這 6 個旋鈕之間找最佳平衡點。

1

Buffer Compression(Qualcomm UBWC / Arm AFBC)

省 DRAM 頻寬最直接的招

把寫進 DRAM 的影像 buffer 無損壓縮(typical 1.5–2×), 或有損壓縮(2–4×)。Qualcomm 的 UBWC(Universal Bandwidth Compression) 是平台級的壓縮格式,camera、display、GPU、encoder 都認得——意思是中間任何一段 round-trip 都省頻寬。 這是 camera 工程師接觸 Qualcomm 平台幾乎必碰的東西。

2

Pipeline Fusion(on-the-fly)

把多個節點串成「跳過 DRAM」

原本是「ISP 寫 DRAM → 後處理讀回 → 再寫 → encoder 讀」。 Fusion 把多個節點直接串接,中間用 SRAM/FIFO,跳過 DRAM round-trip。 最常見:前端 ISP → 後端 ISP → encoder 串成 streaming, 或 ISP → display 直連(preview low-latency)。 代價:fusion 後的 pipeline 不能 stall,任何一段慢就會 back-pressure 整條鏈。

3

Strip / Tile Mode

大圖切塊處理,用 SRAM 換 DRAM 頻寬

一張 50MP 影像 SRAM 裝不下,但切成 N 條 strip 或 N×M tiles 就能。 代價:tile 邊界需要 overlap(halo) 才能跑大 kernel(否則接縫處有 artifact), 這個 halo 重覆讀,反而增加 DRAM 流量。所以 strip 寬度是個 trade-off—— 太窄 halo 比例高、太寬 SRAM 裝不下。Camera 工程師常被叫去 tune 這個。

4

Clock Gating(per ISP block)

idle 的 IP 直接停 clock

ISP 內部分成很多 sub-block(BLC engine、LSC engine、demosaic engine、NR engine…)。 preview mode 用不到 LTM / HDR / MFNR,就把那些 block 的 clock 關掉, dynamic power 立刻歸零。Wake-up cost 極低(ns 級), 所以 frame interval 的 gap 也能 gate。這是你在 MTK 做 PMQoS 應該已經很熟的招,搬過來幾乎無痛。

5

Power Gating(整個 IP 斷電)

leakage 也省,但 wake-up 較貴

不只關 clock,連電源都切掉——leakage power 也省。代價:wake-up cost 上升到 μs 級 (要等電壓穩、register 重新 init)。所以只在「明確會 idle 較久」時才值得—— 例如 video record stop 之後、camera app 切到背景。 判斷時機就是 performance engineer 的工作。

6

DVFS for ISP / DRAM(workload-aware)

不必全速跑就降頻

ISP / DRAM 都支援 DVFS。Preview 30fps 的負載遠低於 capture burst 或 4K@60 錄影, 就該對應跑低頻 / 低壓。判斷依據:frame budget(33ms @ 30fps)還剩多少, 或 SRAM/DRAM 的 backlog 深度。Camera HAL 通常會把這個 hint 透過 PMQoS / interconnect QoS 送下去—— 這條正好是你 PMQoS 經驗的延伸戰場。

Section 06 · Trade-off Matrix

六個旋鈕的代價 面試時要會脫口而出

上面 6 種優化技術,每個都不是免費的。下表把代價列出來—— 面試時你被問「那個方法為什麼不總是用?」,答案就在這。

技術 主要省什麼 代價 誰決定要不要用
UBWC / AFBC DRAM 頻寬(1.5–4×) Silicon area(壓/解壓邏輯)、有損版本損畫質 SoC 架構師(平台層 default on)
Pipeline fusion DRAM round-trip、latency 失去 buffer 容錯;一段慢全條鏈 back-pressure Camera HAL / driver 工程師
Strip / Tile SRAM 面積(不必裝整張) Halo 區重覆讀,反增 DRAM 流量;tune 寬度需經驗 ISP firmware / tuning 工程師
Clock gating Dynamic power(可達 30–60%) 幾乎無代價(ns 級 wake-up) HW 預設 + SW hint
Power gating Dynamic + leakage μs 級 wake-up;狀態要重 init Power policy 工程師
DVFS Power(電壓 × 頻率²) 降太多會 miss frame budget,要 workload prediction Performance / power 工程師(你)
把這張表記成「四象限」
  • 省頻寬(對抗 DRAM 流量):UBWC、Fusion、Strip 寬度
  • 省 dynamic power(對抗 active 時的開銷):Clock gating、DVFS
  • 省 leakage(對抗待機時的開銷):Power gating
  • 共同主軸:都是用 架構複雜度 / silicon area / 開發複雜度 換 power 或 BW
Section 07 · 面試級綜合題

「給你一個 use case 你會怎麼省 power?」

Camera performance 面試最愛問這類開放題。下面拿一個典型題目示範答題框架—— 順序很重要,要從「先確認需求」開始,而不是直接跳到優化技巧。

Q · 4K@60fps 錄影 use case 跑超功耗,你從硬體角度會看哪幾個地方?
1 → 先量,再猜。打開 power/perf profiler 看哪個 block 燒最多——是 ISP、encoder、DRAM、還是 sensor stream?不要先腦補。
2 → 確認 DRAM round-trip 次數。同一張 buffer 被讀寫幾次?有沒有能 fusion 掉的中間落地?(Sec 05 §2)
3 → 檢查 UBWC 是否開啟。Camera→encoder 之間的 buffer 走 compressed format 沒?(Sec 05 §1)
4 → ISP/DRAM clock 是否 over-provisioned。4K@60 frame budget = 16.7ms,目前 ISP 跑完用多久?如果 8ms,代表 clock 開太高 → DVFS 降一檔。(Sec 05 §6)
5 → 有沒有 path 不必要在跑。例如 preview path 在 video 期間還在跑——浪費 sensor stream + ISP power。Camera HAL 該關。
6 → 檢查 memory contention。NPU/GPU/display 是否跟 camera 搶 DRAM 頻寬?PMQoS 仲裁有沒有調好?(這正是你最熟的)
7 → 最後才動畫質。如果以上都掃過還超標,才考慮降 sensor binning、關 LTM、降 NR kernel——這些有 trade-off,要 PM 確認。
答這題你的差異化在哪裡(對你個人)
  • 第 1 步「先量再猜」——你 GenAI 自動化追蹤功耗的經驗能直接搬,談到「我會建一個 dashboard 把這幾個 metric 拉出來」就贏一半
  • 第 4、6 步 DVFS 與 PMQoS 仲裁——這是你的本業,別只說「會用」,要說「PMQoS 從 1ms polling 改 event-trigger 那次,正好處理 idle breaker 的問題」
  • 第 7 步 「最後才動畫質」——這個順序代表你懂 trade-off 的優先級,是 senior 工程師的思維 signal
Section 08 · 本章重點回顧

把硬體層帶進 camera 記這幾件事

硬體層 perf/power 的 5 個核心觀念
1 → DRAM access ≈ 50–100× SRAM access。所有 ISP 架構決策都從這個比例推導
2 → Line / Tile / Frame 三種粒度:能 streaming 的不繞 DRAM,需要看區域/跨幀的就被迫繞
3 → 前端 ISP 便宜、後端 ISP 貴——根源在 SRAM 裝不裝得下處理 window
4 → 6 個優化旋鈕:UBWC、Fusion、Strip、Clock gating、Power gating、DVFS。每個都有代價,要會講代價
5 → DRAM 頻寬就是 PMQoS 的延伸戰場——camera 工程師對 PMQoS 是黑盒,你不是
