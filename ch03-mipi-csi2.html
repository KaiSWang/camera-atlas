Vol. 03 · MIPI & Data Flow

MIPI CSI-2 與資料流
sensor 怎麼把資料 塞進 SoC

Sensor 跟 SoC 之間靠 MIPI CSI-2 講話。它不是「線多就快」,而是一套有 packet、 lane、virtual channel、CRC 的完整協議。理解它,你才能算頻寬、找 EMI、debug 為什麼某個解析度 就是上不去。

Section 01 · 為什麼是 MIPI

從 parallel sensor 到差分串列 歷史的偷懶

2000 年代的 sensor 是 parallel 介面——10 條資料線 + clock + sync,EMI 大、線多、走線難。 手機進入薄型化後,這套行不通了。MIPI Alliance(Mobile Industry Processor Interface) 推出了 D-PHY 和 CSI-2(Camera Serial Interface), 用差分串列搞定一切。

世代 實體層 每 lane 速度 編碼
D-PHY v1.x 差分 LP/HS 雙模式 1.5 Gbps 無
D-PHY v2.5+ 差分 4.5 Gbps 無
C-PHY v1.x 3-wire trio,3-level 2.5 Gsym/s ≈ 5.7 Gbps 3-phase symbol
C-PHY v2.0+ 3-wire trio ~8 Gbps/trio 3-phase symbol
D-PHY vs C-PHY 的取捨
  • D-PHY——4 lane 是標配,每 lane 一對差分線,共 8 條 + clock 2 條 = 10 條
  • C-PHY——3 條一組(trio),不需要額外 clock,因為 clock 內嵌在 symbol 裡。線少 + 速度高
  • 實務上旗艦 sensor(IMX989、HM3)都同時支援兩種模式,PCB 走線決定用哪個
Section 02 · 頻寬計算

算給你看 一張 4K HDR 影片要多少 Gbps

頻寬計算是 camera 系統設計的基本功。基本公式是: bandwidth = width × height × bit_depth × fps × 1.25(overhead)。 乘 1.25 是因為 MIPI 有 packet header、line/frame sync、CRC 等額外負擔。

Scenario · 一個 4K 60fps 10-bit HDR 的影片要多少頻寬?
1 → 3840 × 2160 × 10 bit × 60 fps = 4.98 Gbps(純資料)
2 → × 1.25 overhead = 6.2 Gbps(MIPI 線上的實際流量)
3 → D-PHY 2.5 Gbps × 4 lane = 10 Gbps,夠用
4 → 如果是 staggered HDR(同時送 2 張曝光),× 2 = 12.4 Gbps → 得用 C-PHY 或更高速 D-PHY

旗艦手機常見的 200MP 高解析度模式,raw 資料量大概是 16384 × 12288 × 10 × 30fps × 1.25 ≈ 75 Gbps——這已經完全超過任何 MIPI 規格。 所以實務上 200MP 模式只在拍照模式用,而且 sensor 先做 binning(4-in-1)輸出 50MP, 之後可選擇性升頻到 200MP。

Section 03 · Packet 與 Virtual Channel

CSI-2 是 packet-based 怎麼一條線同時傳多個 stream

CSI-2 的傳輸單位是 packet,不是 raw bit stream。每個 packet 有 header、payload、CRC。 Header 裡有 data type 和 virtual channel ID——這兩個欄位讓「一條 MIPI 線傳多種資料」變得可能。

▸ CSI-2 packet 結構與 virtual channel

CSI-2 packet 結構:Data Identifier(DI)裡的 2 bit VC + 6 bit DT 決定了「這個 packet 是哪個 stream 的什麼格式」。VC0~3 讓一條 MIPI 物理線可同時跑多個邏輯 stream。

為什麼 Virtual Channel 對系統設計重要
  • 多 sensor 共享 MIPI——例如智慧眼鏡兩顆 sensor,可以共用同一個 CSI receiver
  • PDAF metadata 與影像分離——對焦用的相位資料走 VC2,不污染主資料流
  • Sensor embedded data——sensor 把自己的 gain/exposure 設定塞在 VC 裡跟著傳,debug 必看
  • HDR 多曝光——staggered HDR 可以把不同曝光放在不同 VC,後端分流處理
Section 04 · LP / HS 雙模式

D-PHY 的低功耗訊號 idle 時不發狂跑

D-PHY 有兩個工作模式:High-Speed(HS)差分傳資料,Low-Power(LP) 單端發控制訊號。Sensor 不是 24 小時噴 1.5 Gbps,而是「拍到一行 → HS burst → 進 LP idle → 下一行 HS burst」。 這個切換是 EMI 的來源之一,也是功耗大頭。

# D-PHY 一條 lane 的時序 ┌──── HS burst ────┐ ┌──── HS burst ────┐ │ 1.5 Gbps 差分 │ LP-11 │ 1.5 Gbps 差分 │ LP-11 ──┘ 傳一行 raw └─────────┘ 傳下一行 raw └───── ↑ idle ↑ idle HST = HS-transmit LP-11 = 兩線都 high,idle ⚠ HS↔LP 切換太頻繁會引入 EMI 與 timing 風險

實務上你會看到 sensor datasheet 標註 t_HS-PREPARE、t_LPX 等時序參數—— 這些都是 D-PHY spec 規定的切換窗口。SoC 端的 CSI receiver PHY 必須能容忍 sensor 端的時序漂移,所以調 sensor 時若看到 packet error,通常先看 PHY timing tuning。

Section 05 · I²C 控制平面

MIPI 是「資料」I²C 才是「控制」

MIPI CSI-2 只負責從 sensor 到 SoC 的單向資料流。要設定 sensor 的曝光時間、gain、 解析度、輸出格式,得透過另一條線:I²C 或 SCCB(Serial Camera Control Bus,I²C 變體)。 這條控制線決定了 3A 迴路的 latency 下限。

▸ Camera module 完整介面

Sensor 與 SoC 之間至少四種訊號:MIPI(資料、單向高速)、I²C(控制、雙向)、Power rails、MCLK(由 SoC 給 sensor 的參考頻率)。少一條都不會動。

3A latency 為什麼跟 I²C 有關
  • AE 算完新曝光值後,要透過 I²C 寫回 sensor 寄存器
  • I²C 400kHz 時,寫一組 register 大概 200μs,寫一輪所有 3A 設定可能 1~2ms
  • Sensor 內部的「group hold」機制讓多筆設定原子生效,避免半生不熟的曝光
  • 新一代 sensor 改用 I3C(1.6/12MHz),latency 直接降一個數量級
